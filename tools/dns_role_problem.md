
## Роль `dns`: настройка резолвера не всегда доходит до реального резолвинга

Открытый вопрос. Проверка уже добавлена, полное решение отложено.

### Симптом

Роль `dns` отрабатывает без ошибок и рапортует `changed`, но хост продолжает
резолвить через старые адреса. `resolvectl status` показывает две разные
картины одновременно:

```
Global
       DNS Servers: 10.0.0.10 10.0.0.11      <- то, что записала роль
Link 2 (eth0)
       DNS Servers: 8.8.8.8 8.8.4.4          <- то, что реально используется
```

### Почему так

`systemd-resolved` хранит DNS не одним списком, а по scope'ам: глобальный плюс
по одному на каждый сетевой интерфейс. Запросы маршрутизируются по scope'ам, и
интерфейс, у которого есть свои DNS и стоит флаг `+DefaultRoute`, забирает себе
все запросы без совпадающего routing-домена. Глобальный scope при этом остаётся
запасным — он работает только тогда, когда ни один линк не подошёл.

Итог: если у интерфейса с дефолтным маршрутом есть собственные адреса, глобальная
настройка не используется вообще. Не «применяется с меньшим приоритетом», а
просто не участвует.

Адреса на линк попадают с сетевого слоя. Типичные источники:

- `netplan` → `systemd-networkd` (дефолт установщика Ubuntu Server) — секция
  `nameservers` в `/etc/netplan/*.yaml`;
- `cloud-init` — генерирует свой файл в `/etc/netplan/` при каждой загрузке;
- `NetworkManager`;
- DHCP-клиент.

### Дыра в модели роли

Переменная `dns_manager` описывает одну ось — **кто резолвит**
(`resolv_conf` / `systemd_resolved` / `networkmanager`). Осей на самом деле две:

| | вопрос | пример |
|---|---|---|
| резолвер | кто отвечает на запросы | `systemd-resolved` |
| источник | кто скармливает ему адреса | `netplan`, `cloud-init`, DHCP |

`assert_manager.yml` детектит только первую. Он честно находит резолвер, сверяет
с объявленным, совпадение есть — и пропускает дальше. Про вторую ось роль ничего
не знает, поэтому и не замечает, что её настройка перекрыта.

### Что уже сделано

В роль добавлен `tasks/verify.yml`: после применения конфига (и после
`meta: flush_handlers`, чтобы рестарт резолвера успел произойти) роль читает
**фактические** адреса — для `systemd_resolved` это `resolvectl dns` того линка,
у которого стоит `+DefaultRoute`, для остальных менеджеров `/etc/resolv.conf` —
и падает, если они не совпадают с `dns_servers`.

Это не решает проблему, но превращает тихое расхождение в громкую ошибку с
подсказкой, где искать второй источник. Раньше роль в такой ситуации молча
рапортовала успех.

### Что осталось решить

Роль по-прежнему не умеет настраивать сетевой слой. Варианты, если это
понадобится:

1. **Вторая переменная в роли `dns`** (условно `dns_source: netplan`), которая
   кладёт отдельный файл `/etc/netplan/99-ansible-dns.yaml` только с
   `nameservers` для нужного интерфейса. Netplan мержит файлы по порядку имён,
   поэтому `99-` перебивает файл установщика, ничего в нём не редактируя.
   Именно отдельный файл, а не правка чужого: файл от `cloud-init`
   перегенерируется при загрузке и ручные правки в нём не переживут ребут
   (лечится `/etc/cloud/cloud.cfg.d/99-disable-network-config.cfg`).
2. **Отдельная роль для сети**, использующая ту же переменную `dns_servers`.
   Полноценнее, но это заявка на управление адресами, маршрутами и MTU через
   Ansible — большая ответственность ради одного поля.

Оценка: вариант 1 дешевле и достаточен, вариант 2 стоит заводить только если
сеть в целом поедет в Ansible.

Опасное место в обоих вариантах одно — применение. Порядок обязателен:
сначала `netplan generate` (он же валидатор — падает на кривом YAML, ничего не
применив), и только потом `netplan apply`. Это та же идиома «валидируй до
применения», что у `nft -c -f`, `sshd -t` и `nginx -t`.

Отдельно: `netplan generate` **не** применяет изменения, он только
перегенерирует конфиги backend'а в `/run/systemd/network/`. Без `netplan apply`
или перезагрузки ничего не поменяется.

### Ручная диагностика

```bash
resolvectl status            # смотреть целиком, не только секцию Global
resolvectl dns               # адреса по каждому линку
grep -r nameservers /etc/netplan/
```

Роль `server_info` с `metric=dns` показывает адреса именно того линка, у
которого `+DefaultRoute`, то есть те, что реально используются — на её вывод
можно опираться.
