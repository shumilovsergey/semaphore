## Ротация ключа Ansible — `playbooks/identity/`

`~/.ssh/id_ed25519` пользователя, под которым Semaphore запускает
`ansible-playbook`, — это живой ключ, которым он ходит на **каждый** хост парка.
Пропустить при ротации один хост значит потерять к нему доступ насовсем.

`ansible_identity.yml` делает ротацию поэтапной и проверяемой:

```
Стадия 1   server: [OLD]          связь и предусловия, ничего не меняется
Стадия 2   server: [OLD, NEW]     NEW разложен везде, OLD ещё работает
Стадия 3   логин по NEW проверен  с контроллера, на каждом хосте
Стадия 4   server: [NEW]          OLD удалён
```

### Два прогона, а не один

Стадия 4 живёт в **отдельном** прогоне. Между прогонами контроллер уже ходит
новым ключом, а старый ещё лежит на всех хостах — то есть момента, когда у
Semaphore нет рабочего ключа, не существует, и обратная дорога открыта до
самого конца.

```
identity_phase=precheck   только проверки, ничего не меняется
identity_phase=deploy     стадии 1-3, затем бэкап OLD и промоушен NEW
      | прогнать любой обычный плейбук (run.yml, target=all) и убедиться,
      | что Semaphore ходит новым ключом
identity_phase=cleanup    перепроверка NEW и стадия 4
```

### Запуск

Extra Variables в Semaphore:

```json
{
  "target": "all",
  "identity_phase": "precheck"
}
```

`target` обязан быть `all` — плейбук откажется работать с чем-то другим.
Запускать с `--limit` тоже нельзя: он отсекает `localhost` вместе со всеми
проверками, и на границе каждой стадии состав игры сверяется с inventory.

Перед первым прогоном новая пара кладётся на контроллер руками (генерация
появится позже, см. ниже):

```bash
sudo -u ansible ssh-keygen -t ed25519 -N '' -C 'ansible-fleet-2026-08' \
  -f /home/ansible/.ssh/id_ed25519_new
```

Пустой comment запрещён: RouterOS кладёт его в `key-owner` и только по нему
отличает свежеимпортированный ключ от уже лежащих.

### Один файл задач на одну группу

В `tasks/` лежит по файлу на каждую группу inventory, имя файла = имя группы в `inventory/host.ini`. Перед стартом play 0 считает
хосты по группам и складывает: если сумма не сошлась с числом хостов в `all` —
ротация не начнётся. Двух проверок вместе (равенство множеств и равенство длин)
хватает, чтобы гарантировать «каждый хост покрыт ровно один раз».

**Добавил группу в inventory — добавь `tasks/<группа>.yml`.** Иначе плейбук
просто не запустится, и это его главная страховка.

Файлы с префиксом `_` в подсчёт не идут: это общая реализация, которую
подключают обёртки групп.

### Почему у каждой платформы свой файл

Обычный Linux правит `~/.ssh/authorized_keys`, домашний каталог берётся из
`getent passwd`. Termux — тот же файл, но пути зашиты константами: `~` там не
раскрывается, а `ansible_remote_tmp` обязан указывать внутрь Termux. RouterOS
не умеет ни того, ни другого: ни python, ни шелла, только `raw`.

На роутере ключ нельзя «добавить строкой»: файл сначала заливается по scp,
потом импортируется, а удаляется по внутреннему `.id` (`*1`, `*2`). Поэтому
список старых `.id` снимается на стадии 1 фазы `deploy` и доживает до `cleanup`
в файле состояния на контроллере.

Если прошивка не примет ed25519 — положи на контроллер отдельную RSA-пару и
переопредели `identity_mikrotik_new_priv_file` и `identity_mikrotik_new_pub_file`
в `vars/main.yml`. Остальное менять не придётся.

### Проба логина

Стадия 3 логинится с контроллера **новым** ключом:

```bash
ssh -i <new> -o IdentitiesOnly=yes -o IdentityAgent=none -o BatchMode=yes ...
```

`IdentitiesOnly=yes` и `IdentityAgent=none` — несущие опции, а не украшение.
Semaphore держит старый ключ в ssh-agent; без них проба залогинится старым
ключом, отчитается «новый работает», и стадия 4 выкосит весь парк.

### История ключей и откат

Старая пара целиком сохраняется перед промоушеном, каждая ротация — в свой
каталог по дате:

```
~/.ssh/rotation-backup/20260824-193748/id_ed25519
~/.ssh/rotation-backup/20261124-081502/id_ed25519
~/.ssh/rotation-history.log
~/.ssh/rotation-state.yml
```

Из каталога поколений **ничего не удаляется**: каждый когда-либо
использованный ключ остаётся там навсегда — тот, что был в ходу до него,
уезжает в свой каталог при следующей ротации. Единственный ключ, которого в
`rotation-backup/` нет, — действующий, он лежит в `~/.ssh/id_ed25519`.

`rotation-state.yml` живёт один прогон и перезаписывается следующим: из него
фаза `cleanup` читает отпечаток нового ключа и mikrotik-id, снятые в `deploy`.
Историю держит `rotation-history.log`, он только дописывается:

```
20260824-193748  deploy   old=SHA256:bYav... new=SHA256:QAEY...  backup=/home/ansible/.ssh/rotation-backup/20260824-193748
20260824-201133  cleanup  old=SHA256:bYav... removed, new=SHA256:QAEY... in force
```

Две строки на ротацию нужны, чтобы отличить доведённую до конца от брошенной
после `deploy`: у второй строки `cleanup` просто не будет.

Пока фаза `cleanup` не отработала, старый ключ лежит на всех хостах и вернуться
можно одной командой:

```bash
cp ~/.ssh/rotation-backup/<дата-время>/id_ed25519* ~/.ssh/
```

После `cleanup` откат уже невозможен — на хостах остался только новый ключ.
